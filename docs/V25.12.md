# v25.12 — ปิดช่องที่เหลือ: /ping ก็ต้องพิสูจน์ว่ารัน Lua จริง (เหมือน /auth และ /stage)

## ตรวจสอบทั้งระบบตามที่สั่ง พบว่า
- `/auth` (ขอ token/key) — **มีระบบพิสูจน์อยู่แล้ว** (`lib/proof.js`: `checkChallenge`/`proofRequired`) บอทที่ยิง POST ตรง ๆ ไม่มี `sc`/`pf` ที่ถูกต้องให้แนบ ผ่านไม่ได้อยู่แล้ว
- `/stage` (ขอสคริปต์จริง) — **มีระบบพิสูจน์อยู่แล้ว** (`stageProofOk` คนละชุดกับของ /auth แต่หลักการเดียวกัน)
- `/ping` (รายงานว่ากำลังเล่นอยู่ ทุก 10 นาที) — **ไม่มีเลย** ก่อนหน้านี้ใครก็ยิง POST/GET ตรง ๆ ใส่ค่า u/n/d/h อะไรก็ได้โดยไม่ต้องรัน Lua จริงสักบรรทัด ← จุดนี้แก้ใน v25.12
- `/loader`, `/bootstrap-source`, `/bootstrap-info` — เป็นจุด "เริ่มต้น" ก่อน Lua จะรันได้เลยสักครั้ง จึงพิสูจน์แบบนี้ไม่ได้โดยธรรมชาติ (ต้องรัน Lua ก่อนถึงจะพิสูจน์ว่ารัน Lua ได้) อาศัยการที่ขั้นต่อไป (auth/stage/ping) มีการพิสูจน์แทน

## สิ่งที่แก้
- `lib/vault.js`: `tracker()` ฝัง challenge + โปรแกรมพิสูจน์การรัน Lua (ชุดเดียวกับที่ `/auth` ใช้) ไว้ในโค้ดติดตามผู้เล่น คำนวณครั้งเดียวก่อนเริ่มลูป ping แนบ `sc`/`pf` ไปกับทุกครั้งที่ ping
- `app/ping/[code]/route.js`: ถ้าคำขอแนบ `sc`/`pf` มาแต่ไม่ถูกต้อง (ปลอม/หมดอายุ/คนละ IP) → ถือว่าน่าสงสัยมาก (`strike` เหมือนจุดอื่น ๆ) และปฏิเสธทันที
- **ไม่ทำลายของเก่า**: ถ้าคำขอไม่มี `sc`/`pf` เลย (สคริปต์รุ่นก่อน v25.12 ที่กำลังรันอยู่ในเกมตอนนี้) ยังผ่านได้ตามปกติ ไม่บล็อก เพื่อไม่ให้คนที่กำลังเล่นอยู่ตอนอัปเดตโดนตัดกลางคัน

## ทดสอบแล้ว
- โค้ด Lua ที่ `tracker()` สร้าง: สุ่ม 15 ครั้ง ผ่านไวยากรณ์ Lua ทุกครั้ง
- จำลองการคำนวณ proof ฝั่ง Lua จริง (`proofExpect`) แล้วเทียบกับ `checkChallenge` ฝั่งเซิร์ฟเวอร์: proof ถูกต้อง+IP ตรง → ผ่าน · proof ผิด → ปฏิเสธ (`reason:'proof'`) · IP ไม่ตรง → ปฏิเสธ (`reason:'ip'`) ตรงตามที่ออกแบบไว้ทุกกรณี
- `next build` ผ่านทั้งโปรเจกต์
- ยังไม่ได้ทดสอบบน Roblox executor จริง — ควรลองรันลิงก์จริงอย่างน้อย 1 ครั้งก่อนใช้งานจริงทั้งระบบ (ping ครั้งแรกควรผ่านปกติ ไม่โดนบล็อก)
